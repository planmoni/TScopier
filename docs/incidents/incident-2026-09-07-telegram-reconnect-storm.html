1. Executive summary (plain English)

What this incident is about, in plain English:

  • A user told us he could not connect his Telegram account. While investigating, we found the same problem was affecting three other accounts.
  • Behind the scenes, each of these accounts' listeners was flapping — dropping its connection to Telegram and trying to reconnect every twenty seconds, for hours, without ever settling into a stable "connected" state. A watchdog probe (a lightweight ping to Telegram every 30s) correctly detected that the connections had gone zombie and asked the worker to reconnect — but the reconnect itself had no time limit and got stuck, so every new attempt was handed the same stuck one.
  • While a listener was flapping, the app could not even request a fresh login code: the code requests hung and timed out after 90 seconds (this happened 7 times for one user alone).
  • Three separate things were wrong: (1) a counting bug meant the safety mechanism that should have restarted a stuck listener never fired; (2) the reconnect step had no time limit, so a network hang could freeze it permanently; (3) a single mistyped login code was treated as a dead end and forced the user to restart the whole login, even though Telegram allows retrying the same code.
  • We fixed all three in the worker and improved the on-screen guidance so users know the login code arrives inside the Telegram app, not as a text message.
  • Expected result after the fix is deployed: a stuck listener recovers or is cleanly restarted within about a minute instead of flapping for hours, and a mistyped code no longer forces a full restart.

1b. What "flapping" means here

What TScopier does: TScopier listens to trading-signal Telegram channels on behalf of each user and copies the signals to their broker. For each connected user, our worker runs a "listener" — a background connection to Telegram that stays open so it can catch new signals the moment they are posted.

What flapping is: "Flapping" is when that connection drops and reconnects over and over without ever staying connected. A listener briefly drops for many ordinary reasons (a network blip, Telegram being slow), and it is normal for it to reconnect a second or two later. In this incident the reconnect attempt got stuck (it waited forever instead of failing fast), so the listener never actually reconnected, and the twenty-second health-check kept finding it broken and kept kicking it — hours of on/off flapping.

Why it matters to the user: While flapping, the user's copier engine looks offline, and — worse — the same stuck reconnect also blocked the login flow, so the user could not even request a new verification code to reconnect their account. Flapping is a symptom; the underlying causes are the two bugs in section 4 (a counter that never accumulated, and a reconnect with no time limit).

1c. The story: what happened, in order

This is the whole incident told as a single, plain-English narrative — from the first report to where things stand now.

  1. The report. On 2026-09-07 a user, Marcin Adamczyk (mrfun1981@gmail.com), told us he could not connect his Telegram account. A second user reported the same problem. This looked at first like a login problem, so that is where we started looking.
  2. What we found in the logs. His login had actually worked earlier that day — at 15:38 he connected successfully using the QR-code method, and our worker began listening to 27 of his channels. But three minutes later the watchdog noticed his connection had gone quiet and asked the worker to reconnect. That reconnect never finished.
  3. The reconnect got stuck. A watchdog probe every 30 seconds tests the connection by calling updates.GetState — a lightweight ping to Telegram. Two consecutive failures mean the socket is a zombie: it looks open, but Telegram is not responding. The probe failed twice, so the watchdog asked the worker to reconnect. That reconnect tried to open a fresh connection to Telegram, but Telegram did not answer, and the code had no time limit, so it waited forever. From that moment the listener was stuck half-connected: the health-check ran every twenty seconds, found it still broken, and tried again — but every "try again" was handed the same stuck attempt instead of starting a fresh one. The account flapped like this for hours.
  4. The safety net was also broken. Normally, after about three failed reconnect attempts the worker gives up on that listener and restarts it cleanly, which would have fixed everything within a minute. But a counting bug meant the failure counter was reset to zero on every check, so the count could never reach three and the restart never happened.
  5. Login then became impossible. While the listener was stuck, any attempt to request a new login code hung too — the worker could not reach Telegram at all — and timed out after 90 seconds. This happened seven times. So the user was caught in the worst of both worlds: he was not connected, and he could not reconnect.
  6. It was never just him. The same flapping was happening to other accounts in lockstep, which told us the cause was on our worker's side, not something the user had done. As of 2026-09-08, six accounts were flapping and the storm was still live in production.
  7. Separately, the login flow punished a simple typo. Even when a code did arrive (inside the Telegram app, not as an SMS), one wrong digit destroyed the whole login and forced a fresh start — even though Telegram allows retrying the same code. This made an already confusing experience much more painful.
  8. What we fixed. (a) The failure counter now accumulates while a listener is broken, so a stuck listener is cleanly restarted after about a minute. (b) Every step of reconnecting now has a 45-second time limit, so nothing can hang forever — and stopping a listener can no longer be blocked either. (c) A wrong login code is now retryable instead of fatal. (d) The on-screen guidance now makes it unmissable that the code arrives inside the Telegram app, and always offers a "Send a new code" action.
  9. Where it stands now. The fixes are written, tested (48 worker tests, 2 frontend tests, typechecks and lint all green), reviewed, and committed to the staging branch. They are not yet deployed, so the storm is still affecting production. The moment the worker deploys to staging (then production), the flapping should stop and affected users should be able to connect again — using the QR method, or by phone and checking the Telegram app for the code.

4. Root cause

How the system is meant to work: Every twenty seconds the worker checks each user's listener and renews a "lease" that says "I am the copy handling this Telegram account, nobody else should touch it." If a listener is not connected, the worker tries to reconnect it; and after a few failed tries it is supposed to tear the listener down and start it fresh. Two bugs defeated that plan.

Each cause, in plain English and then in technical detail:

  1. The "how many times has it failed" counter was being reset every tick, so the restart safety net never fired.

    Plain English: The worker was counting how many times in a row the listener had failed to reconnect, planning to restart it after about three failures (~60 seconds). But because of a misplaced line, the counter was cleared back to zero on every single check — even while the listener was still broken. So the count could never reach three, the restart never happened, and the listener flapped forever.

    Technical: In worker/src/sessionManager.ts, renewOneListenerLease increments disconnectedRenewTicks when the listener is down and, after disconnectedRenewHealTicks() (default 3 ≈ 60s) consecutive failures, hard-resets the listener (stop + syncSessions restart). But line 408 executed this.disconnectedRenewTicks.delete(userId) unconditionally on every tick — including while disconnected — so the counter never accumulated past 1 and the hard-reset never fired. The lease kept being renewed, so no other worker replica could take the user over either.

  2. The reconnect step had no time limit, so a network hang froze it forever — and every later retry was handed the same frozen attempt.

    Plain English: When the worker tried to reconnect a listener, it opened a connection to Telegram and waited. If Telegram did not answer, the code just sat there waiting — there was no "give up after 45 seconds" limit. Once that happened, every later reconnect request was given the same stuck attempt instead of trying again, so no new reconnect ever actually ran. This is why the flapping never healed on its own.

    Technical: In worker/src/userListener.ts, forceReconnect called client.connect() and the updates.GetState() probe with no timeout. A hung MTProto socket (Telegram DC unreachable) left the reconnectInFlight promise pending forever. requestReconnect returns the existing in-flight promise when one is set (line ~4508), so every subsequent reconnect request became a no-op and no new force reconnect ever ran — confirmed: the last force reconnect log for af75b63e was 15:41:30. stop() also awaited reconnectInFlight with no bound, so a wedged reconnect blocked disconnectTelegramSession and the lease hard-reset too.

  3. Two knock-on hazards made things worse: a timed-out connect could double-connect, and a stopped listener could be re-connected.

    Plain English: Once we add a timeout (see section 5), two secondary dangers appeared. First, if a connection attempt timed out but was still finishing in the background, the next retry could open a second connection on the same Telegram account at the same time — Telegram treats that as a conflict and can drop the session. Second, if a user disconnected their account while a reconnect was mid-flight, the worker could finish reconnecting a listener that had already been told to stop.

    Technical: The retry loop could call client.connect() again while the first (timed-out but still running) connect completes in the background, risking a double connection on the same auth key (AUTH_KEY_DUPLICATED). The loop also only checked stopping at the top of each iteration, so a stop() could return while the loop was still mid-connect and re-establish a live socket on a stopped listener.

  4. A single mistyped login code destroyed the whole login, even though Telegram allows retrying it.

    Plain English: If a user typed the verification code with one wrong digit, our system treated it as a dead end, wiped the login in progress, and forced the user to request a brand-new code and start over. Telegram actually keeps the login valid across wrong attempts, so this made a trivial typo much more painful than it needed to be — and combined with the code arriving in the Telegram app (not SMS), it was a real source of user frustration.

    Technical: worker/src/telegramAuthRecovery.ts classified PHONE_CODE_INVALID as fatal, destroying the pending auth and forcing a full send_code restart. Telegram keeps the phoneCodeHash valid across wrong-code retries; the code is only invalidated by expiry or a fresh send_code.

  5. The on-screen guidance was too easy to miss when the code arrives inside the Telegram app.

    Plain English: When Telegram delivers the login code inside the app itself (which is what it did for these accounts) rather than by SMS, the screen only showed a small line of text saying so. And if that code expired, the user was left on the code screen with no obvious "send a new code" action, unsure what to do next.

    Technical: In src/components/telegram/TelegramConnectFlow.tsx, when codeDelivery === 'app', the only guidance was a small hint line; after a code expired there was no resend/new-code affordance on the code screen (resend button only showed when canResend).

Why the user-visible symptom has happened before with different root causes: This is the same class of incident (users unable to connect Telegram, delivery=app codes never entered) that previously produced write-ups on 2026-08-14, 2026-08-19 and 2026-09-01. Each time the underlying mechanism was different. The 2026-09-01 "Ruth" fix (2d4c5cb0) addressed a stuck authInFlight in the auth path (see section 8). The flapping loop described here lives in the listener reconnect path and was not covered by that fix.

5. The fix

Worker + frontend changes; committed to staging (not yet deployed at time of writing). Each fix, in plain English and then technical detail:

  1. Let the restart safety net actually fire.

    Plain English: We moved the "reset the failure counter" step so it only runs when the listener is genuinely back online. Now the count of consecutive failures builds up while the listener is broken, and after about three failures the worker tears the listener down and starts it fresh — exactly as it was always meant to.

    Technical: worker/src/sessionManager.ts — moved disconnectedRenewTicks.delete(userId) into the connected (else) branch so the counter accumulates across disconnected ticks and the hard-reset fires after disconnectedRenewHealTicks() failed ticks.

  2. Put a time limit on every reconnect step.

    Plain English: Every step of reconnecting a listener now has a 45-second cap (configurable). If Telegram does not answer within that time, the attempt is abandoned and treated as failed instead of hanging forever — so a network problem can no longer freeze the listener or block the login flow. Stopping a listener can no longer be blocked by a stuck reconnect either.

    Technical: worker/src/userListener.ts — added withTelegramTimeout() (async race helper) and telegramConnectTimeoutMs() (env TELEGRAM_CONNECT_TIMEOUT_MS, default 45s, clamped 5–120s). Wrapped client.connect(), the updates.GetState() probe, disconnect(), and stop()'s await on reconnectInFlight.

  3. Stop the two knock-on hazards (double-connect and reconnecting a stopped listener).

    Plain English: When a connection attempt times out, we now close the socket cleanly before trying again, so a slow background connection cannot sneak in and create a second connection on the same Telegram account. And the reconnect routine now checks "has this listener been told to stop?" after every step, so it can never bring a stopped listener back to life.

    Technical: worker/src/userListener.ts — added if (this.stopping) { disconnect; return/break } after every connect/probe await in both forceReconnect and reconnectAndRetryDialogs, plus a disconnect-before-retry in the transient-error path (prevents AUTH_KEY_DUPLICATED). Post-loop warmup also guards on stopping.

  4. Let a mistyped login code be retried instead of killing the login.

    Plain English: A wrong verification code no longer wipes the login in progress. The user can simply re-enter the correct code. Only an expired code (or requesting a fresh code) starts a new login — matching what Telegram actually allows.

    Technical: worker/src/telegramAuthRecovery.ts — PHONE_CODE_INVALID is now recoverable (keeps the pending auth so the user can retry); PHONE_CODE_EXPIRED remains fatal.

  5. Make it obvious where the login code arrives, and always offer a way forward.

    Plain English: When Telegram delivers the code inside the app, the screen now shows a clear, unmissable message: "Open Telegram on your phone … The code is NOT sent by SMS." And there is now always a "Send a new code" button on the code screen, so if the code expires or is missed, the user has a straightforward action instead of being stuck.

    Technical: src/components/telegram/TelegramConnectFlow.tsx — prominent callout when codeDelivery === 'app'; always-visible "Send a new code" button (when canResend false) re-requesting via send_code through a new onRequestNewCode prop; wired in CopierEnginePage.tsx and TelegramLinkStep.tsx via a shared requestCode() helper.

  6. Localized the new text.

    Plain English: The new messages are translated for all languages the app supports.

    Technical: Added tgConnectCodeAppHint + sendNewCode keys to en/es/fr/ar and pl/ru/sv/nl/ja (copierEngine bundle) + types.ts.

8. How this ties to the 2026-09-01 fix

In plain English: This is not the first time users could not get a Telegram login code, and it is worth explaining how this incident relates to the fix we made on September 1 ("the Ruth fix"), because the two incidents share a surface symptom but had different underlying causes — and both fixes are needed.

  • The September 1 problem: a login-code request could get stuck waiting to take over the account, and while it was stuck, every new request was refused with "a login is already in progress." That fix added a time limit (90 seconds) and an auto-expiry (2 minutes) to the login request part of the flow, so a hung login could never block future logins forever. Those settings are unchanged and still in place today.
  • The September 7 problem (this report): the stuck part was not the login request — it was the listener reconnect. The September 1 timeout protected the login path (which is exactly why these users' code requests failed cleanly after 90 seconds instead of hanging), but it did not put any time limit on reconnecting the listener itself. That unlimited wait is what wedged the listener and produced the flapping loop.
  • Why both fixes are needed: the September 1 fix keeps login requests from hanging; this fix keeps a broken listener from flapping forever and from blocking new login attempts. Together they cover both halves of the flow.

9. What to expect after deploy

  • A disconnected listener now recovers or is cleanly restarted within ~60 seconds (default LISTENER_DISCONNECT_HEAL_TICKS = 3 × 20s renew interval), instead of flapping for hours.
  • A network hang can no longer freeze reconnect indefinitely — each connect/probe/disconnect step is bounded (45s default), and stop() cannot be blocked by a wedged reconnect.
  • A mistyped login code no longer destroys the pending login — the user can simply re-enter the code. Only an expired code (or a fresh send_code) starts a new login.
  • Users connecting by phone see a clear message that the code arrives inside the Telegram app (not SMS) and always have a "Send a new code" action.
  • Important: Telegram controls delivery. The login code will still be delivered inside the Telegram app for these accounts (delivery=app); we cannot force an SMS. Users must open Telegram on their phone and look for the message from Telegram.
