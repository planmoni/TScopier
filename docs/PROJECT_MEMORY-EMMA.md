### 2026-08-25 - Critical Sentry Runtime Health For FxSocket And Worker Liveness

- **Context:** A sustained FxSocket/API disconnect was not previously surfaced as a critical Sentry incident. The worker had substantial Sentry coverage for fatal exceptions and user-impacting business events, but the FxSocket WebSocket reconnect path could keep retrying with only local logs and no engineering alert when market-data/socket infrastructure stayed unavailable.
- **Responsibility boundary:** Sentry critical health now answers "is TScopier runtime or infrastructure broken?" Admin/logging remains the source of truth for "why did this user's signal, trade, or account behave this way?" Individual rejected trades, malformed signals, user/account configuration failures, normal broker business rejections, and recoverable trade-level outcomes intentionally remain admin/business diagnostics unless they indicate a systemic outage.
- **Architecture:** Added `worker/src/observability/criticalHealth.ts` as a health state/event model, not a second Sentry transport layer. It defines bounded component/failure metadata, process-local cooldown suppression, resource-id hashing, `captureCriticalHealthIssue(...)`, and `SustainedOutageTracker`. It delegates actual Sentry transport to the existing `worker/src/observability/sentry.ts` helper, preserving existing redaction, scope, tags, fingerprints, and fire-and-forget behavior.
- **FxSocket behavior:** `worker/src/fxsocketWsClient.ts` now wires WebSocket lifecycle events into a sustained-outage tracker. A short disconnect inside `FXSOCKET_SOCKET_OUTAGE_GRACE_MS` stays log-only. If the current socket remains unavailable beyond the grace period, the worker emits one critical-health event with `component=fx_socket`, `failure_class=sustained_outage`, `provider=fxsocket`, and reason code `FXSOCKET_SOCKET_SUSTAINED_OUTAGE`. Reconnect attempts continue normally and update metadata; successful reconnect resets outage state so a later legitimate outage can alert again.
- **Race hardening:** Every socket-bound handler for the captured `const ws = ...` now checks active identity before mutating connection or health state: stale `open`, `message`, `close`, and `error` events are ignored when `this.ws !== ws`. This prevents an old socket's late close from scheduling reconnect or starting a false outage timer after a replacement socket is already healthy.
- **Timer invariant:** `SustainedOutageTracker.scheduleAlert()` enforces one active grace timer per active outage. First disconnect schedules the timer; repeated reconnect attempts only update metadata and do not allocate additional timers. Recovery clears the timer. After the timer fires, state handling remains valid; after recovery, a future outage gets a fresh timer.
- **Dedupe/grouping:** FxSocket sustained-outage cooldown is provider scoped inside one worker process: `fx_socket|fxsocket|<platform>|<endpoint_host>`. It excludes account/user identity and excludes API keys or query parameters. Multiple FxSocket clients in one worker share process-local suppression, but equivalent events from separate worker processes can still reach Sentry. The shared fingerprint `critical_health / fx_socket / sustained_outage / fxsocket` groups equivalent events into the same Sentry issue across workers.
- **Worker heartbeat:** Added guarded `captureWorkerCheckIn(...)` in the existing Sentry helper and `worker/src/observability/workerHeartbeat.ts` for opt-in Sentry monitor check-ins. `worker/src/index.ts` starts heartbeat check-ins only when `SENTRY_WORKER_HEARTBEAT_MONITOR_SLUG` is configured and stops the interval during shutdown. This detects missed check-ins/process liveness only; it does not prove the trade/copier pipeline is actively processing work. `/health`, queue metrics, copier health rows, and admin diagnostics remain necessary for readiness and workflow-level health.
- **Runtime isolation:** Monitoring is isolated from WebSocket runtime behavior. `FxsocketWsClient` calls monitor methods through a local `reportHealth(...)` wrapper, and Sentry helpers catch their own failures. A disabled/missing/throwing Sentry SDK path cannot break socket open/message/close handling, reconnect scheduling, queue processing, or trading behavior. Invalid JSON frames no longer update last-success activity metadata.
- **Security/privacy:** Critical-health metadata is bounded and sanitized. It can include component, failure class, severity, state, environment, provider, platform, endpoint host, reconnect attempt/delay, duration, and hashed account/resource identifiers. It must not include FxSocket API keys, auth tokens, credentials, raw Telegram messages, raw signal payloads, broker payloads, account balances/equity/free margin, request/response bodies, or full endpoint URLs with query strings.
- **Env vars:** Added `SENTRY_CRITICAL_HEALTH_ENABLED=true`, `SENTRY_CRITICAL_HEALTH_COOLDOWN_MS=300000`, `FXSOCKET_SOCKET_OUTAGE_GRACE_MS=60000`, `SENTRY_WORKER_HEARTBEAT_MONITOR_SLUG=`, `SENTRY_WORKER_HEARTBEAT_ENABLED=true`, `SENTRY_WORKER_HEARTBEAT_INTERVAL_MS=60000`, and `SENTRY_WORKER_HEARTBEAT_CHECKIN_MARGIN_MINUTES=2` to `worker/.env.example`. - **Resend behavior:** Added worker `/auth/resend_code`, Edge action `resend_code`, shared frontend typing, and dashboard/onboarding resend actions. Before Telegram's timeout expires, resend is rejected locally with the remaining wait. After timeout, the worker calls `Api.auth.ResendCode` using the existing phone number and current server-side hash, consumes the returned `auth.SentCode`, and replaces the old hash with the returned hash as the single authoritative hash.
